我建了一个仓库：https://github.com/lusgli-0/learning-group

里面现在只有一个 README.md。这周要做的事很简单：把你自己的 GitHub 主页地址（比如 https://github.com/lusgli-0）写进这个文件，然后发一个 Pull Request（PR）请求合并。

PR 就是「我改了东西，请你看一下，觉得行就合并进去」。这是团队协作最核心的动作，也是我们之后一直要做的事。

操作流程：

Fork → Clone → 建分支 → 修改 → commit → push → 发 PR

看着有点多，其实是一个完整闭环，照着做一遍就会了，不会的直接问 AI。PR 合并之后，你自己那个分支就可以删掉了。

有了这份 README.md，我们就能互相串门看对方的代码了。所以这个部门从现在开始有三条流程：

一、个人代码放个人仓库，自己设置 public / private

公开的代码如果希望别人使用或修改，就写一个 README.md，并选一个 license。这样有两个好处：代码始终是你自己的，而且可以展示，可以直接当简历用。

二、主要靠两个渠道交流：Issue 和 PR

Issue 用来提问、讨论、报 Bug；PR 用来提交改动。GitHub 之外，群里、社区里聊，或者直接给我发消息都可以。

三、尽量每周开一次分享会

暂定 3 人轮班，一人提前写一个最小的可复现例子公开到仓库里，然后讲 15 分钟。这个会主要是为了建立线下的关系、锻炼表达能力（包括我自己）、以及把一件事讲清楚来加深理解。

本来这些内容是要在第一次分享会上讲的，拖到现在，只能先用文字说明。

我在这里承诺：只要各位把自己的账号写进那个仓库的文档里，我有时间就一定会去看你们的代码，随机挑问题、随机改 Bug，要是我修不动，就开个issue，我来帮你把问题问清楚。 就算是纯 AI 写的代码，只要功能不错，我也会帮忙整理和重构（架构好不好我不打包票，但会认真看）。

大家也可以互相看代码，遇到小 Bug 自己修，然后提 PR。说到底，最重要的还是自己动手写。

分享会的内容我会整理成最小可复现例子放进仓库，至少保留一周，没听到的可以补；但看十遍不如自己敲一遍。
